# 运维手册

## 首次接入（按顺序做，别跳）

```bash
# 1. 初始化（会写 panel.config.json + 建库 + 建管理员）
python3 -m cpapanel init --node http://127.0.0.1:8317 --node-key sk-你的管理密钥

# 2. 启动（Web + 采集线程 + 巡检线程）
python3 -m cpapanel serve --host 127.0.0.1 --port 18317

# 3. 看一次巡检计划 —— 此时 dry_run 还是开的，不会动任何东西
python3 -m cpapanel inspect

# 4. 观察几天，确认计划合理后再打开 apply（见下）
```

第 3 步的 `inspect` 会打印**它打算做什么**。等你确认这些动作都对（比如「额度耗尽的号禁用、需重登的号进备用池」），
再决定是让服务常驻巡检，还是用 cron 跑：

```bash
# 打开真正执行（两种方式选一）
#   a) 在面板的「设置」页把 inspector.dry_run 关掉，服务内的巡检线程就会执行（推荐）
#   b) 不用服务内巡检线程，交给 cron：
python3 -m cpapanel serve --no-inspector        # 只留 Web + 采集线程
*/15 * * * * cd /path/to/cpa-panel && python3 -m cpapanel inspect --apply
```

> ⚠️ **采集不要交给 cron**：cron 最快也只能每分钟一次，而上游队列只保留 ~60 秒，
> 每分钟采一次会丢数据。采集就用服务内置线程（15 秒一轮）；
> 确实要外置调度，请用短循环而不是 cron：
>
> ```bash
> * * * * * cd /path/to/cpa-panel && timeout 55 sh -c 'while true; do python3 -m cpapanel collect; sleep 15; done'
> ```
>
> 并且注意：**不要与面板的采集线程同时跑**（见下文「队列被抢」）。

`collect` / `inspect` 在**采集失败或存在失败节点时返回非 0**，可以直接给监控用。

> ⚠️ 不要把 `collect` 和面板的采集线程**同时**跑在同一个 CPA 上 —— 见下面的「队列被抢」。

## 日常该看什么

| 看哪里 | 说明 |
| --- | --- |
| 概览页 | 就绪率、熔断横幅、低水位告警、用量趋势；有熔断横幅就先看它 |
| 凭证页 | 按状态筛选；「需重登」是需要人工介入的唯一一类 |
| 巡检页 | 每轮计划与执行结果；失败动作会标红 |
| 审计 | 谁在什么时候做了什么（包括每次危险操作） |

## 故障处置

### 巡检触发了熔断

现象：概览出现「就绪率过低，本轮未执行任何维护动作」，`mode = circuit_break`。

含义：**面板主动停手了**。它认为「这么多号同时坏」更像上游事故，而不是「这些号都该删」。

处置顺序：

1. 先看上游：是不是被封了 / 网关挂了 / 网络不通（`curl <CPA>/v1/models` 试一下）。
2. 看是「集体 401」还是「集体额度耗尽」—— 前者多半是风控，后者可能是共享额度的正常表现。
3. 确认确实该清理，再手动处理（凭证页批量操作），或临时把 `inspector.min_ready_ratio` 调低。
4. **不要**为了让巡检继续跑就把 `delete_*` 打开 —— 那正是熔断要防的事。

### 某个号一直「冷却中」想立刻复用

```bash
python3 -m cpapanel cool codex-3.json     # 或面板上该行的「重置冷却」
```

上游只接受 `auth_index`，CLI 会自己把本地记录或上游快照里的 `auth_index` 找出来。

### 大量号变成「需重登」

- 先确认不是误判：面板的判定区分**强/弱证据**，弱证据（只有文案）只会「标记」不会动手。
  看凭证详情里的「判定依据」，如果是弱证据，说明只是文案像，不代表号真的废了。
- 如果确实是 `token expired` / `invalid_grant`，只能人工重新走 OAuth（面板的「OAuth」页）。

### 采集有缺口 / 用量少了一截

1. 看审计里的 `collector.gap`：说明两次成功采集之间超过了阈值。
2. **最常见的原因是在同一个 CPA 上还跑着别的采集器**（见下）。
3. 其次是面板进程被停过、或上游重启导致队列里的记录已过期（60 秒 TTL，过期即丢）。

### 队列被抢（会导致数据静默丢失）

上游的用量队列是**消费型**的：谁取走就是谁的，取走的记录别人再也拿不到，且只保留约 60 秒。

所以：**同一个 CPA 实例，同一时间只应该有一个采集器在消费队列**。
如果你还跑着别的面板/统计工具（很常见），两边都会拿到**不完整的**数据，而且**不报错**。

处置：

- 只留一个采集器（推荐留本面板，因为它是秒级采集 + 落库）；
- 或者让所有采集器都改用上游的**订阅模式**（这种情况下上游不再往队列投递，就不会互相抢）。

### 管理 API 返回 404 / 401

| 现象 | 原因 |
| --- | --- |
| 所有 `/vN/management/*` 都是 **404** | 上游**没有配置管理密钥**（注意：不是 401）。配置密钥后重启上游 |
| **401** | 密钥不对；或面板里存的密钥与该节点不匹配 |
| 只有部分端点 404 | 上游版本较老，没有 v8 端点；把节点前缀改成 `v0`，或看 [upstream-api.md](upstream-api.md) 的能力边界 |

## 危险操作

| 操作 | 防护 |
| --- | --- |
| `POST /api/credentials/delete-all` | 必须带 `confirm=DELETE-ALL`；不可逆；巡检**永远不会**调用它 |
| 批量删除 | 受 `inspector.max_deletes_per_run`（默认 20）限制，手点也一样 |
| 替换上游 config.yaml | 全量替换语义：写坏了上游就起不来。改之前先备份 |
| 打开 `delete_unauthorized` / `delete_quota_exhausted` | 强烈建议保持关闭，用「禁用 / 备用池」代替 |

## 备份与恢复

```bash
# 备份（SQLite 用 WAL，先 checkpoint 再拷更稳）
python3 -m cpapanel prune --help >/dev/null     # 顺手确保服务在跑同版本
cp panel.config.json panel.config.json.bak
cp data/panel.db data/panel.db.bak

# 恢复：停服务 → 换回两个文件 → 起服务
```

配置与数据是**两个**文件：`panel.config.json`（服务参数、节点列表的引导信息）+ `data/panel.db`（账号、令牌、历史、审计）。
只备份数据库会丢节点引导信息，只备份配置会丢全部历史。

## 数据保留

`prune` 默认：用量明细 180 天、凭证采样 30 天、审计 90 天。聚合表（`usage_daily`）不参与清理，
所以趋势图在明细被清掉后依然完整。
